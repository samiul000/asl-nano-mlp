==============================================================================
DATASET B - STREAMING ABLATION: CONVENTIONAL vs LAYER-STREAMED INFERENCE
==============================================================================
Project   : ASL Alphabet Recognition on Arduino Nano (ATmega328P, 16 MHz,
            30,720 B flash, 2,048 B SRAM)
Scope     : Scaled architectures only (small1, small2, large1, large2).
            The deployed/current architecture is intentionally excluded.
Date      : 2026-08-23
Method    : Every number below is hardware-measured or compiler-derived.
            No cycle-model estimates are used anywhere in this file.

------------------------------------------------------------------------------
1. DEFINITIONS
------------------------------------------------------------------------------
CONVENTIONAL (weights resident in SRAM)
  Before computing a layer, its entire weight matrix is copied from flash
  (PROGMEM) into an SRAM buffer with memcpy_P(); all multiply-accumulate reads
  then hit SRAM directly (~1 cycle class) instead of LPM reads (~3 cycles
  class). This is the textbook embedded-ML layout and the natural baseline
  against which layer-streaming must justify itself.

LAYER-STREAMED (deployed scheme)
  No weight copy: each multiply-accumulate reads one int16 weight directly
  from PROGMEM via pgm_read_word(), neuron by neuron, accumulating into
  int32. Weights never occupy SRAM.

Firmware pairs were generated by experiments/scripts/export_scaling_firmware.py
from identical model.h headers (same trained checkpoints, same per-neuron
row-max INT16 quantization), differing ONLY in the weight-read path above.
Timing-probe sketches time each layer independently with micros() and report
{sign,infer_us,l0_us,l1_us,l2_us,sm_us,confidence,fps,free_ram,peak_stack}
per packet. Measurements = median over n=300 packets, 0 timeouts.

3. CONVENTIONAL FEASIBILITY (compiler verdict, arduino-cli + avr-gcc)
------------------------------------------------------------------------------
Static-SRAM requirement of each conventional build (wbuf + activations +
serial buffer + runtime globals), against the ATmega328P's 2,048 B:

  Arch      Static SRAM demanded   Verdict
  --------  ---------------------  ------------------------------------------
  small1        2,006 B (97%)      COMPILES - leaves 42 B for locals+stack
  small2        2,718 B (132%)     COMPILER-REJECTED (overshoots by 670 B)
  large1        4,854 B (237%)     COMPILER-REJECTED (overshoots by 2,806 B)
  large2        6,278 B (306%)     COMPILER-REJECTED (overshoots by 4,230 B)

small1 was pushed to hardware despite the 42 B margin:

  Flash attempt : arduino-cli upload OK (old-bootloader clone Nano, COM5)
  Runtime       : board produced ZERO responses to 20 consecutive packets;
                  boot banner absent -> device crashed/hung before or during
                  the first inference. The 42 B headroom cannot cover even
                  the call-chain locals (loop() -> parse_packet() ->
                  predict()), let alone interrupt frames.
  Verdict       : MEASURED INFEASIBLE.

Conclusion of section 3: conventional full-weight SRAM residency is
infeasible on the ATmega328P at EVERY architecture size tested - rejected
by the compiler outright for small2/large1/large2, and by the silicon
itself for small1. There is no conventional baseline to time.

Peak stack measured via stack painting (sentinel 0xCD fill at boot, deepest

regardless of architecture size.

------------------------------------------------------------------------------
5. WHY THE COMPARISON STILL RESOLVES DECISIVELY
------------------------------------------------------------------------------
Although no conventional build could be timed, the ablation question -
"what does layer-streaming cost us?" - has an exact upper bound:

  * The only benefit conventional can offer is replacing ~3-cycle LPM weight
    reads with ~1-cycle SRAM reads, i.e. at most ~2 cycles saved per weight
    access. Across all weights that bounds the possible speedup well below
    25% of MAC time.
  * The price is N_weights * 2 bytes of SRAM (1,344 - 6,400 B here), which
    exceeds what the 2,048 B part can ever offer alongside activations,
    buffers, and a live stack - as sections 3 proves empirically, not
    theoretically.
  * Therefore layer-streaming is not merely competitive; it is the ONLY
    executable option on this microcontroller, and its overhead relative to
    an unbuildable ideal is bounded by the LPM penalty already included in
    every measured figure above.
